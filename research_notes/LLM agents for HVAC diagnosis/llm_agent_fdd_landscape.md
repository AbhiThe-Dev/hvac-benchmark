# LLM Agents for HVAC/Building Fault Detection, Diagnosis, and Maintenance — Landscape Survey (2023–2026)

## What notable papers/systems exist where an LLM agent has tool-calling access to FDD software, BAS data, or maintenance databases?

### Takeaway
The field is small and young: most "LLM for HVAC FDD" work published 2023–2025 uses the LLM as a fine-tuned or prompted **classifier** over sensor time-series (no tool-calling at all), while genuine tool-orchestrating agents — where the LLM decides which data source or sub-tool to query next — are a distinctly newer (2025–2026) and much rarer subset, and often not published in top building-science venues yet (arXiv preprints, one industry GitHub project, one Q&A-framework paper). A 2026 platform paper (Buildrix) explicitly states that most existing agentic building-engineering demos are "isolated proof-of-concept demonstrations" lacking standardized evaluation — corroborating that the space is immature.

### Cited Findings
- **JARVIS** — a master-worker LLM framework for natural-language interaction with sensor-driven HVAC data. An "Expert-LLM" (LLaMA3.1-8B-Instruct) interprets a user query and generates structured execution instructions; a separate Python Agent executes these through query-execution, data-processing, and response-generation modules (i.e., the LLM does not touch the database directly but plans and dispatches queries/statistical analyses). Authors: Sungmin Lee, Minju Kang, Joonhee Lee et al., Yonsei University / POSTECH / University of Michigan / LG Electronics. arXiv:2507.04748, submitted July 7, 2025. — [alphaXiv overview](https://www.alphaxiv.org/overview/2507.04748) / [arXiv](https://arxiv.org/abs/2507.04748)
- **LLM-driven multi-agent framework for FDD of VAV terminal units** — uses a "GBF" (Gaia–BDI–FIPA) multi-agent architecture with three cooperating agents: a **Planner** that interprets expert rules into executable diagnostic tasks, an **Executor** that performs quantitative analyses with iterative self-correction, and a **Reporter** that integrates verified results into interpretable health assessments. Published in *Architectural Engineering and Design Management*, Vol. 22, No. 3 (2026). — [Taylor & Francis](https://www.tandfonline.com/doi/abs/10.1080/17452007.2026.2647805)
- **hvac-field-service-agent** (GitHub, author "YangLiu68") — an open-source/portfolio project (explicitly **not** a peer-reviewed paper or production system) combining a FastAPI backend and React/TypeScript console. The LLM acts as an orchestrator via function-calling: it receives a restricted set of permitted tools per workflow "skill," proposes tool calls, and receives structured results, iterating — while the server (not the model) enforces argument validation, job-state rules, duplicate-call blocking, step limits, and audit records. Tool set includes read-only tools (`get_job_context`, `get_equipment_profile`, `search_service_manuals`, error-code lookup, verified-repair lookup) and workflow tools (`request_technician_measurement`, `record_measurement`, `create_diagnostic_hypothesis`, status updates, human escalation). — [GitHub](https://github.com/YangLiu68/hvac-field-service-agent)
- **Buildrix** — an open platform (CLI package + web "Hub" + local agent harness) for sharing and benchmarking agentic AI skills in building engineering, explicitly covering fault detection, diagnosis, and maintenance-recommendation skill categories among others. Authors: Zixin Jiang and Bing Dong. arXiv:2606.25139, June 23, 2026. The authors' own framing: "most existing applications remain isolated proof-of-concept demonstrations and lack reusable domain capabilities, human-verified evaluation cases, and standardized benchmarking infrastructure" — a direct, citable statement about the state of the broader field. — [arXiv](https://arxiv.org/abs/2606.25139)
- **Context-aware LLM-based AI Agents for Human-centered Energy Management Systems in Smart Buildings** — Tianzhi He, Farrokh Jazizadeh (Virginia Tech), arXiv:2512.25055, January 2026. References Brick schema, BIM, EnergyPlus simulation, and vector databases (Milvus/FAISS) as candidate data sources/tools for an agent framework; framed around energy management rather than explicitly FDD. — [arXiv](https://arxiv.org/pdf/2512.25055)
- By contrast, several prominent "LLM for HVAC fault diagnosis" papers involve **no tool orchestration** at all: e.g., Langer, Hirsch, Kern, Kohl, and Schweiger, "Large Language Models for Fault Detection in Buildings' HVAC Systems," presented at the 4th Energy Informatics Academy Conference (EI.A 2024, Kuta, Bali, October 2024; published in Springer's *Energy Informatics* proceedings 2025) — fine-tunes DistilBERT directly on HVAC time-series to classify fault conditions (F1 up to 99%), with no agentic/tool-calling component. — [Springer](https://link.springer.com/chapter/10.1007/978-3-031-74741-0_4) / [ACM DL](https://dl.acm.org/doi/10.1007/978-3-031-74741-0_4)
- Similarly, "Domain-specific large language models for fault diagnosis of heating, ventilation, and air conditioning systems by labeled-data-supervised fine-tuning," *Applied Energy* (2025), fine-tunes GPT-3.5 on labeled fault/fault-free HVAC data with a self-correction strategy for generating the fine-tuning set; the resulting model is dimension-independent across different sensor configurations, but functions purely as a classifier, not an orchestrating agent. — [ScienceDirect](https://www.sciencedirect.com/science/article/pii/S0306261924017616)
- "Physics-Informed Large Language Models for HVAC Anomaly Detection with Autonomous Rule Generation," Subin Lin and Chuanbo Hua, arXiv:2510.17146 (October 21, 2025) — uses an LLM to autonomously generate interpretable physics-informed detection rules (a knowledge-extraction/reasoning role) rather than as a classifier or full orchestrator; positions itself against traditional rule-based FDD (Katipamula 2005) and deep-learning/transformer anomaly detectors (Zhang 2023; Karpontinis 2024). — [arXiv](https://arxiv.org/pdf/2510.17146)
- Adjacent (generic industrial, not building-specific, but architecturally transferable): "A Trustworthy Industrial Fault Diagnosis Architecture Integrating Probabilistic Models and Large Language Models," arXiv:2510.03815, reports improved diagnostic accuracy of "more than 28 percentage points" over baseline models while reducing calibrated expected calibration error (ECE) by "more than 75%" — not HVAC-specific but a relevant hybrid probabilistic+LLM architecture pattern. — [arXiv](https://arxiv.org/abs/2510.03815)

### Inferences
- The distinction the objective asks about (orchestrator vs. classifier vs. report generator vs. knowledge extractor) maps cleanly onto a **chronological split**: 2023–2024 work is almost entirely classifier-style (fine-tuning LLMs on sensor data), while genuine tool-orchestrating agent architectures (JARVIS, the VAV Planner/Executor/Reporter framework, hvac-field-service-agent, Buildrix) cluster in 2025–2026, suggesting the "agentic" framing is a recent trend layered on top of an older fine-tuning-focused literature.
- Peer-reviewed, indexed venues (ASHRAE Transactions/Journal, *Energy and Buildings*, *Automation in Construction*, ACM BuildSys proceedings) were not found to contain a fully agentic, multi-tool-orchestrating HVAC FDD system in this search; the clearest orchestrator examples are either arXiv preprints, a peer-reviewed-but-less-prestigious "Architectural Engineering and Design Management" journal, or non-peer-reviewed open-source/industry projects. This suggests genuinely validated, top-venue agentic FDD work may not yet exist in volume, or was not surfaced by this search.

### Gaps
- Direct search of ACM BuildSys, ASHRAE Transactions/Journal, and IBPSA/SimBuild proceedings specifically (rather than general web search) was not performed due to tool-call budget; a dedicated conference-proceedings search could surface additional 2024–2026 papers not indexed well by general search.
- Full text of several papers (VAV multi-agent framework behind a Taylor & Francis paywall; OpenReview PDF blocked by a bot-check page) could not be retrieved, so architectural/evaluation details beyond what abstracts and secondary summaries reveal are incomplete for those two sources.

## For each system, what was the LLM's actual functional role?

### Takeaway
Only a minority of surveyed systems have the LLM genuinely deciding "what to query next" across multiple tools/data sources (orchestrator); most either classify fault labels directly from data (classifier), or synthesize/reason over already-verified diagnostic steps into a written assessment (report generator / reporter role embedded within an orchestrator pipeline). Pure "knowledge extractor" roles (pulling facts from documents/manuals) appear mainly as one tool among several inside a larger orchestrator (e.g., `search_service_manuals` in hvac-field-service-agent) rather than as a standalone system.

### Cited Findings
- **Orchestrator**: JARVIS's Expert-LLM "doesn't directly access databases but generates parameterized instructions that guide SQL queries and statistical analysis," executed by a separate Python Agent — a clear plan-then-dispatch orchestration pattern over real sensor data. — [alphaXiv](https://www.alphaxiv.org/overview/2507.04748)
- **Orchestrator (multi-agent, role-decomposed)**: In the VAV FDD framework, the Planner "interprets expert rules into executable diagnostic tasks," the Executor "performs quantitative analyses with iterative self-correction," and the Reporter "integrates verified results into interpretable health assessments" — i.e., orchestration (Planner), execution/tool-use (Executor), and report generation (Reporter) are explicitly separated into different agent roles within one system. — [Taylor & Francis](https://www.tandfonline.com/doi/abs/10.1080/17452007.2026.2647805)
- **Orchestrator with hard server-side guardrails**: In hvac-field-service-agent, the LLM "proposes tool calls" and iterates, but "the server — not the model — remains responsible for argument validation, job-state rules, duplicate-call blocking, step limits, audit records, and terminal states," making the LLM's orchestration role deliberately bounded/non-authoritative over consequential actions. — [GitHub](https://github.com/YangLiu68/hvac-field-service-agent)
- **Classifier**: Langer et al. fine-tune DistilBERT directly on HVAC time-series to output fault-condition labels (F1 up to 99%) — no tool use, no multi-step reasoning, no orchestration. — [Springer](https://link.springer.com/chapter/10.1007/978-3-031-74741-0_4)
- **Classifier**: The *Applied Energy* (2025) domain-specific LLM fine-tunes GPT-3.5 on labeled fault/fault-free data to output diagnoses directly, emphasizing transferability across sensor configurations rather than tool orchestration. — [ScienceDirect](https://www.sciencedirect.com/science/article/pii/S0306261924017616)
- **Knowledge extractor / rule generator**: The physics-informed HVAC anomaly detection paper uses the LLM to autonomously generate interpretable detection rules — a reasoning/knowledge-synthesis role distinct from both classification and orchestration. — [arXiv](https://arxiv.org/pdf/2510.17146)

### Inferences
- Systems that explicitly decompose LLM responsibilities into named sub-roles (Planner/Executor/Reporter, or Expert-LLM/Python-Agent) appear to produce more auditable and better-evaluated systems (both the VAV framework and JARVIS report concrete quantitative comparisons against baselines — see next question), suggesting that role decomposition, not a single monolithic "agent," is the emerging best practice distinguishing genuine orchestration from a chatbot front-end.
- The user's own related work (noted in local memory: a documentation-mismatch benchmark using "sequential Bayesian active testing," and a `symptom_pipeline`/`hvac_benchmark` codebase) is conceptually adjacent to this survey — it appears to already implement an evidence-driven, tool-orchestrating diagnostic approach rather than a report-generator, which is consistent with the more rigorous end of what this survey found in the wider literature. (This is local context, not an external citable source.)

### Gaps
- Could not confirm the functional role of the Context-aware LLM-based AI Agents for Smart Buildings paper (arXiv:2512.25055) in detail — the fetched PDF excerpt only allowed an inference ("appears to function as an orchestrator") based on title and reference list, not confirmed architectural description.

## How were these systems evaluated, and at what sample sizes?

### Takeaway
Evaluation rigor varies enormously and correlates with publication type: the two peer-reviewed-adjacent papers (JARVIS, VAV multi-agent framework) report real data with concrete sample sizes and human evaluation, while the open-source/industry project explicitly self-labels its evaluation as too small to be meaningful, and several arXiv preprints could not be confirmed to report any quantitative evaluation at all from the accessible content.

### Cited Findings
- **JARVIS**: evaluated on "real-world data collected from a commercial HVAC system and a ground truth QA dataset curated by HVAC experts," plus a human user study with **22 participants** validating automated LLM-as-a-Judge assessments (both automated and human-centered evaluation used). — [alphaXiv](https://www.alphaxiv.org/overview/2507.04748)
- **VAV multi-agent framework**: evaluated via a case study on **29 VAV boxes**, comparing framework outputs to manually labeled ground truth — described as a retrospective case study using real building data rather than a live, continuously-operating deployment. — [Taylor & Francis](https://www.tandfonline.com/doi/abs/10.1080/17452007.2026.2647805)
- **hvac-field-service-agent**: evaluation consists of **60 labeled HVAC cases** spanning six diagnostic categories (`evaluation/agent_cases.jsonl`) plus a **five-case retrieval benchmark**, explicitly described by the author as "intentionally small and must not be presented as production accuracy." The reported evaluation is an "offline policy regression (no actual LLM calls)" measuring routing accuracy, tool sequences, diagnosis accuracy, escalation metrics, and latency — i.e., a synthetic regression-test suite, not a real-building or real-technician deployment. — [GitHub](https://github.com/YangLiu68/hvac-field-service-agent)
- **Buildrix**: emphasizes "standardized benchmarking infrastructure" with test cases "verified by domain experts" and promoted to "golden test cases for reproducible benchmark evaluation," but specific sample sizes or completed benchmark results were not available in the accessible abstract/introduction content. — [arXiv](https://arxiv.org/abs/2606.25139)
- **Industry claim (not academically evaluated)**: Siemens' March 2025 press release for its Industrial Copilot for Maintenance claims "initial pilot applications" showed the tool can "cut reactive maintenance times by an average of 25%" — no sample size, methodology, or building/plant count disclosed. — [Siemens press release](https://press.siemens.com/global/en/pressrelease/siemens-expands-industrial-copilot-new-generative-ai-powered-maintenance-offering)

### Inferences
- None of the surveyed HVAC/building-specific agentic systems report evaluation across **multiple buildings** at scale; the largest confirmed sample size in a real/near-real evaluation is 29 VAV units (single case study) and JARVIS's single commercial HVAC system. This suggests external validity (generalization across building types, climates, equipment vendors) is essentially unestablished for agentic FDD systems as of this search.
- Given how small and explicitly-flagged-as-non-production the hvac-field-service-agent evaluation is, and how vague the Siemens industry claim is, the field currently has essentially **no large-N, real-deployment, agentic-LLM-vs-technician evaluation** for HVAC FDD specifically.

### Gaps
- Could not retrieve full evaluation methodology/results for the Physics-Informed HVAC Anomaly Detection paper (arXiv:2510.17146) or the Context-aware Smart Building Agents paper (arXiv:2512.25055) — PDF extraction returned only front-matter/reference-list content, not the results sections.
- No large-scale (multi-building, multi-season) field trial of an agentic (tool-orchestrating) LLM system for HVAC FDD was found in this search; it is unclear whether such a study exists but was not surfaced, or genuinely does not yet exist.

## What comparison baselines were used?

### Takeaway
Where baselines are reported, they are almost always **other LLM configurations** (a monolithic/single-LLM baseline, a text-to-SQL baseline, ablated components) rather than a rule-based commercial FDD tool or a human technician — meaning claims of "LLM agent outperforms X" mostly demonstrate agentic decomposition beats a naive LLM, not that LLM agents beat established engineering practice.

### Cited Findings
- **VAV multi-agent framework**: baseline is a "monolithic LLM baseline" (i.e., a single non-decomposed LLM attempting the same FDD task); the multi-agent Planner/Executor/Reporter framework "significantly outperforms" it in task completeness, execution reliability, and diagnostic accuracy, and achieves "complete consistency with manually labeled ground truths." — [Taylor & Francis](https://www.tandfonline.com/doi/abs/10.1080/17452007.2026.2647805)
- **JARVIS**: primary baseline is **TAG**, a Text2SQL framework; JARVIS is also compared against ablated versions of itself (component-wise ablation study). Reported failure rates for the text-to-SQL baseline approach: "complex SQL generation failures (43.2%)" and "null value handling issues (32.4%)," which JARVIS's parameterized query-building was designed to address. Query execution accuracy for JARVIS: 92%, with 90% recall and 100% precision; user-study scores averaged 4.0+/5 for cohesiveness and truthfulness, 3.7/5 for helpfulness. — [alphaXiv](https://www.alphaxiv.org/overview/2507.04748)
- **Physics-informed HVAC anomaly detection**: positions itself conceptually against traditional rule-based FDD (Katipamula 2005) and deep-learning/transformer anomaly detectors (Zhang 2023; Karpontinis 2024) in its framing, but specific quantitative head-to-head comparison numbers were not retrievable from the accessible PDF content. — [arXiv](https://arxiv.org/pdf/2510.17146)
- No system in this search was found to report a **human-technician baseline** (e.g., time-to-diagnosis or accuracy comparison against a certified HVAC technician) for an agentic/tool-orchestrating system specifically — the closest is JARVIS's human-participant *evaluation of the AI's output quality*, which is not the same as a technician-vs-AI diagnostic accuracy comparison.
- Adjacent generic-industrial example: "A Trustworthy Industrial Fault Diagnosis Architecture" (arXiv:2510.03815) reports "more than 28 percentage points" accuracy improvement over unspecified "baseline models," illustrating the pattern of comparing against other model baselines rather than human or established-tool baselines. — [arXiv](https://arxiv.org/abs/2510.03815)

### Inferences
- The absence of rule-based-commercial-FDD-tool or human-technician baselines across every system found suggests that, as of this search (September 2026), no HVAC-specific agentic LLM paper has yet made a rigorous, quantified "AI agent vs. status-quo practice" claim — all quantified comparisons found are LLM-architecture-vs-LLM-architecture (agentic decomposition vs. monolithic prompting, or vs. text-to-SQL).

### Gaps
- Could not determine whether any HVAC-specific agentic system has been benchmarked against a commercial rule-based FDD product (e.g., a whole-building diagnostic tool from a major BAS vendor) — this would be a valuable comparison this search did not surface.

## What is explicitly claimed as validated vs. anecdotal/unvalidated?

### Takeaway
Authors of the more careful academic/open-source sources are notably self-critical and explicit about the limits of their own evidence (hvac-field-service-agent, Buildrix); industry marketing claims (Siemens, and general "GenAI cuts downtime 25–40%" market commentary) are stated with much more confidence but essentially no disclosed methodology, sample size, or peer review, and should be treated as unvalidated.

### Cited Findings
- hvac-field-service-agent's author explicitly flags the five-case retrieval benchmark as "intentionally small and must not be presented as production accuracy," and states the whole evaluation suite provides only a "safety and routing regression baseline," not a production-quality or clinical-grade validation claim. The README further states: "This repository demonstrates system architecture and evaluation workflows. It is not a certified diagnostic product and must not replace qualified HVAC technicians or manufacturer safety procedures." — [GitHub](https://github.com/YangLiu68/hvac-field-service-agent)
- Buildrix's authors explicitly characterize the *existing* field (not just their own prior work) as consisting of "isolated proof-of-concept demonstrations" lacking "reusable domain capabilities, human-verified evaluation cases, and standardized benchmarking infrastructure" — an explicit, citable acknowledgment from within the research community that most claims in this space are currently anecdotal/unvalidated at scale. — [arXiv](https://arxiv.org/abs/2606.25139)
- By contrast, industry sources state efficiency numbers with high confidence and low transparency: Siemens claims its Industrial Copilot for Maintenance can "cut reactive maintenance times by an average of 25%" based on unspecified "initial pilot applications" (March 2025), and general market commentary states "Generative AI is already slashing unplanned downtime by 25–40%" — these are industry claims (not peer-reviewed, no disclosed sample size, methodology, or building/plant count) and should be labeled as such, not treated as validated results. — [Siemens](https://press.siemens.com/global/en/pressrelease/siemens-expands-industrial-copilot-new-generative-ai-powered-maintenance-offering) / [Drives&Controls](https://drivesncontrols.com/16519-2/)
- JARVIS's reported metrics (92% query execution accuracy, 90% recall, 100% precision, human study n=22) are disclosed with a specific evaluation methodology and dataset, making them a comparatively well-validated (if narrow, single-system, single-building) result. — [alphaXiv](https://www.alphaxiv.org/overview/2507.04748)
- The VAV multi-agent framework's "complete consistency with manually labeled ground truths" on 29 VAV boxes is a concrete, disclosed result, but it is a single retrospective case study (not a live deployment or multi-building trial), so the claim should be read as "validated on this one case-study dataset," not generalized. — [Taylor & Francis](https://www.tandfonline.com/doi/abs/10.1080/17452007.2026.2647805)

### Inferences
- There is a clear, citable pattern of **academic/open-source authors under-claiming** (explicitly caveating small-N results) versus **industry press-release claims over-claiming** (aggregate percentage improvements with no disclosed methodology) — this asymmetry itself is a notable landscape finding worth flagging to the report writer.

### Gaps
- No independent, third-party validation or replication of any of these claims (academic or industry) was found in this search.

## What failure modes or limitations are reported?

### Takeaway
HVAC/building-specific sources report mostly *system-design* limitations (small-N evaluation, synthetic vs. real deployment gap, restricted/guardrailed tool access), while the more severe failure modes conventionally worried about for LLM agents in safety-critical domains — hallucinated causes, novel-equipment brittleness, prompt-engineering fragility, cost/latency — are documented primarily in **adjacent** domains (aerospace, medical, general industrial fault diagnosis) rather than being empirically demonstrated in HVAC-specific studies found in this search, which is itself a notable gap.

### Cited Findings
- **Safety-gating as an implicit acknowledgment of risk**: hvac-field-service-agent's extensive guardrail design — a deterministic preflight graph constraining diagnosis steps before LLM involvement, a skill registry limiting which tools the LLM can call per workflow, mandatory human-approval gates for high-risk operations (refrigerant measurements, electrical work, component replacement), a technician feedback loop, and a requirement that unverified diagnoses never enter historical case memory — is itself evidence that the author considers unconstrained LLM tool-calling unsafe for real HVAC field actions. — [GitHub](https://github.com/YangLiu68/hvac-field-service-agent)
- **From an adjacent (non-HVAC) but relevant fault-tolerant-control agent study**: "From Detection to Action: Using LLM Agents for Fault-Tolerant Control" reports GPT-4o-mini succeeded in 51 of 60 runs (85%) across fault scenarios, with failures concentrated in pump-degradation and sensor-fault scenarios; failure analysis identified "unnecessary activations in pump degradation where the Action Agent activated the main pump despite degradation conditions," described as a "separation-of-concerns violation." (Domain not confirmed as building/HVAC-specific — appears to be general process-control simulation — but architecturally transferable as a documented LLM-agent failure mode in a fault-response setting.) — [arXiv](https://arxiv.org/pdf/2606.28011)
- **Text-to-SQL baseline failure modes** (motivating JARVIS's design): "complex SQL generation failures (43.2%)" and "null value handling issues (32.4%)" when a naive LLM is asked to directly query sensor databases in natural language — a concrete, quantified failure mode for the "just let the LLM write queries" approach to BAS data access. — [alphaXiv](https://www.alphaxiv.org/overview/2507.04748)
- **General LLM hallucination risk in safety-critical domains** (not HVAC-specific, but relevant context per the objective's failure-mode question): benchmarking work on LLMs for hazard analysis in safety-critical systems notes that inaccurate hazard identification "could compromise system safety and potentially lead to severe harm," and that hallucination issues are "exacerbated in low-probability, high-stakes scenarios such as rare adverse safety events" (documented in aerospace-manufacturing and medical contexts, with reported hallucination rates as high as 65–88% in some specialized-domain evaluations). No HVAC-specific hallucination-rate study was found. — [ScienceDirect](https://www.sciencedirect.com/science/article/pii/S0925753525002814)
- **Explicit non-deployment disclaimer**: hvac-field-service-agent's README states deployment would require "real SMS/CRM adapters, production identity management, multi-tenant security, and significantly expanded case validation before" any real-world/clinical-grade use — i.e., the author explicitly does not consider the current system ready for real HVAC operations. — [GitHub](https://github.com/YangLiu68/hvac-field-service-agent)

### Inferences
- The near-total absence of HVAC/building-specific empirical failure-mode studies (hallucinated fault causes, novel-equipment brittleness, cost/latency measurements) suggests this is an open research gap: the community appears to be more focused on demonstrating capability (can an LLM agent diagnose faults at all) than on stress-testing failure modes, safety, or cost/latency trade-offs specific to building systems.
- The consistent presence of heavy guardrails/human-in-the-loop design (both in the open-source project and implicitly in the VAV framework's "verified results" language) suggests practitioners in this space already assume LLM agents are not yet trustworthy enough for autonomous action on HVAC equipment, even where they are trusted for diagnosis/recommendation.

### Gaps
- No HVAC/building-specific study quantifying hallucination rate, cost, or latency of an LLM agent in FDD was found in this search.
- No study addressing how these agents perform on truly novel/unseen equipment types (out-of-distribution generalization) was found for the building domain specifically.
- Full text of several papers only partially extracted (openreview.net blocked by bot-check; Taylor & Francis abstract page returned 403; several PDFs returned only front-matter via WebFetch's summarizer) — a follow-up pass with direct PDF download/OCR rather than WebFetch's HTML-oriented summarizer could recover the missing limitations/results sections for: the VAV multi-agent paper, the "Advancing Building Autonomy with LLM-Based Fault..." OpenReview paper (id=6duZh6rQhI, could not be identified beyond the URL), the Buildrix benchmark results, and the Context-aware Smart Building Agents paper (arXiv:2512.25055).
