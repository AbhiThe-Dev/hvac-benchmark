## Q1. How LLM agents are used for RCA/incident investigation, reported accuracy vs non-LLM baselines, and any head-to-head of LLM probe choice vs an information-theoretic selector

### Takeaway
Across ~25 systems/benchmarks, the LLM's role is almost never "choose the next probe by information value": production systems fix the data-collection order with human-authored handlers, SOPs, workflows, or graph constraints and use the LLM to summarize, classify, or explain; free-form ReAct agents that do choose probes score low (11-25% on realistic benchmarks) and waste steps. I found NO published head-to-head of an LLM's next-query choice against an entropy/expected-information-gain selector in AIOps or network operations; the only information-theoretic active-probing work (IBM, 2002-2005) is pre-LLM and reports 60-75% fewer probes than non-adaptive probing. Classical/non-LLM RCA is still state of the art for fast metric-only localization (e.g., 68% Top-1 in 8 ms), while LLM agents win only on heterogeneous text/log evidence and explanation, at 100-1000x latency.

**RCACopilot (Microsoft, EuroSys 2024) [V]** — [arXiv 2305.15778](https://arxiv.org/pdf/2305.15778)
1. Mapping: hypothesis space = root-cause category labels (long-tailed); probe = data-collection actions inside per-alert-type "incident handlers" (human-built workflows); evidence = aggregated diagnostic info; stop = handler completes; cost = wall-time (4.2 s inference) — [paper](https://arxiv.org/pdf/2305.15778).
2. LLM role: summarizes handler-collected diagnostic data, then predicts category via retrieval of similar historical incidents (few-shot) and writes an explanation. It does NOT choose what to collect; handlers are constructed manually by on-call engineers and updated by them — [paper](https://arxiv.org/pdf/2305.15778).
3. Eval: 653 real incidents from Microsoft's Transport (email) service over one year, 75/25 train/test, three rounds; Micro-F1 0.766, Macro-F1 0.533 (GPT-4); baselines XGBoost, FastText, fine-tuned GPT-3.5, GPT-4-prompt-only, GPT-4+embeddings all much lower (Micro-F1 0.02-0.26, long-tail labels). Handler diagnostic collection in production >4 years across 30 teams — [paper](https://arxiv.org/pdf/2305.15778).
4. Failure/not shown: baselines are weak text/ML classifiers, not causal/graph RCA; the paper itself lists "outdated information" in troubleshooting guides (TSGs) as a core pain point (new checks not added to TSG after feature release) and motivates dynamic, engineer-updated handlers — [paper](https://arxiv.org/pdf/2305.15778).
5. Non-LLM SOTA? Not compared. The human-authored handler (i.e., the selector) is the non-LLM component that has been in production the longest.
6. Transfer: the closest industrial precedent for "documentation (TSG/handler) goes stale and a formal/curated layer must decide what to collect while the LLM only interprets"; also evidence that documented procedures decay silently.

**LLM ReAct agent for cloud RCA (Roy et al., Microsoft, FSE 2024 companion) [S]** — [arXiv 2403.04123](https://arxiv.org/html/2403.04123v1)
1. Mapping: free-text root-cause prediction for production incidents; probes = tool calls (incident-detail QA, historical-incident retrieval, KBA QA, Pandas DB queries, ask-human); stop = final answer or 20-step cap.
2. LLM role: GPT-4 ReAct agent autonomously selects tools (it does choose the next lookup).
3. Eval: 107k Microsoft incidents (2020-21) split 102k/2k/3k; analysis on 500 test incidents. ReAct correctness ~35% vs CoT ~39% vs retrieval ~39%, but hallucination ~4% (ReAct) vs ~12% (CoT) vs ~40% (retrieval-only). Avg ~4 unique historical retrievals + ~2 lookups per incident.
4. Failure: 66% of incorrect ReAct answers cited insufficient evidence (32% for CoT); agent exhausted step limit on incidents needing multi-KBA workflows; difficulty formulating distinct retrieval queries.
5. Non-LLM SOTA? Not compared (only retrieval/CoT baselines).
6. Transfer: tool-using agent buys factuality (fewer hallucinations) rather than accuracy; nothing on query efficiency.
(Source for all: [arXiv HTML](https://arxiv.org/html/2403.04123v1); numbers via fetch summary [S].)

**RCAgent (Alibaba Cloud, CIKM 2024) [V for design, N unverified]** — [arXiv 2310.16340](https://arxiv.org/pdf/2310.16340)
1. Mapping: RCA for Flink jobs; probes = log/metric/code tools via agent; stop = controller finalization.
2. LLM role: controller agent + expert sub-agents (log agent does chunked RAG and must copy evidence verbatim to curb hallucination); "trajectory-level self-consistency" samples only at finalization (10 samples) to save cost; internally deployed Vicuna-13B on one A100 for privacy — [paper](https://arxiv.org/pdf/2310.16340).
3. Eval: superior to ReAct on root cause/solution/evidence/responsibility by automated metrics and human evaluation; integrated into Alibaba Cloud's Real-time Compute Platform for Apache Flink. Sample size not verified — [ACM/arXiv abstract](https://arxiv.org/abs/2310.16340).
4. Failure/not shown: no non-LLM comparison; evaluation is text-similarity + human rating.
5. Non-LLM SOTA? Not addressed.
6. Transfer: self-consistency over the action trajectory is a cheap variance-control device; relevant to run-to-run inconsistency.

**Flow-of-Action (CAS/ByteDance/Tsinghua, WWW 2025 companion) [V]** — [arXiv 2502.08224](https://arxiv.org/abs/2502.08224)
1. Mapping: microservice RCA; probes = tools invoked along an SOP-derived flow; stop = a Judge agent says stop.
2. LLM role: retrieves/generates SOPs (documented operating procedures), converts to code, multi-agent execution; the SOP flow constrains which tool comes next (ReAct alone "hallucinates irrelevant actions").
3. Eval: 90 injected incidents on Online Boutique (Chaos Mesh, 9 fault types). Location/Type accuracy: ReAct GPT-4-Turbo 47.67/23.33 (avg 35.50), Reflexion GPT-4T avg 29.06, Flow-of-Action GPT-4T 70.89/57.12 (avg 64.01); avg path length (steps) ReAct 10.76 vs Flow-of-Action 15.10, i.e., MORE steps but more accurate. Ablation (GPT-3.5): removing SOP knowledge 54.06 -> 15.39; removing SOP flow -> 27.50 — [paper](https://arxiv.org/pdf/2502.08224).
4. Failure/not shown: baselines are LLM frameworks plus K8sGPT/HolmesGPT; no classical RCA; synthetic injected faults on one small system.
5. Non-LLM SOTA? Not compared.
6. Transfer: strongest evidence that a procedure/flow outside the LLM (documented SOP) is worth more accuracy than model choice; it did not reduce query count.

**mABC (multi-agent blockchain-inspired voting; EMNLP Findings 2024) [V]** — [arXiv 2404.12135](https://arxiv.org/abs/2404.12135)
1. Mapping: microservice RCA over a global topology; seven agents incl. "Dependency Explorer" that queries the (trusted, given) topology and "Probability Oracle"; step cap and workflow to avoid non-terminating loops from circular dependencies.
2. LLM role: agents vote (weighted) to reduce hallucination.
3. Eval (Table 4, avg of root-cause/path accuracy): Decision Tree 31.6, MEPFL 30.7, TraceAnomaly 22.0, ReAct GPT-3.5 26.6, ReAct GPT-4T 38.5, mABC GPT-4T 46.9 (Train-Ticket dataset + AIOps-challenge dataset). Path length: mABC GPT-4T 10.4/11.7 vs ReAct GPT-4T 13.9/14.3 vs Decision Tree 12.1/13.4 — [paper](https://arxiv.org/pdf/2404.12135).
4. Failure/caveat: the paper's prose reports different averages (e.g., mABC 64.9, ReAct 27.5) than its own Table 4 — internal inconsistency; treat headline claims cautiously. Independent evaluation found mABC generating non-existent service names ([GALA, S](https://arxiv.org/abs/2608.08968)) and near-minimal reasoning rounds ([trajectory study, V](https://arxiv.org/abs/2608.21310)); OpsHarness reports mABC at 5.6% top-1 on OpenRCA/RCAEval ([S](https://arxiv.org/abs/2608.25661)).
5. Non-LLM SOTA? Baselines are old/weak (decision tree, TraceAnomaly, MEPFL), not CIRCA/BARO/RCD.
6. Transfer: even here the dependency graph is an input assumed correct.

**Meta Platforms AI-assisted investigation RCA (Engineering blog, June 2024) [S]** — [blog](https://engineering.fb.com/2024/06/24/data-infrastructure/leveraging-ai-for-efficient-incident-response/)
1. Mapping: hypothesis space = candidate code changes for a monorepo incident; probe = none (retrieval/ranking, not interactive).
2. LLM role: two stages: heuristic retrieval (code ownership, directory, runtime code graph) cuts thousands of changes to a few hundred; a fine-tuned Llama-2 7B ranks (max 20 changes per prompt, "election" aggregation, log-prob ranking) to a top-5.
3. Eval: backtesting, 42% root cause in the top 5 at investigation creation time; total N not disclosed.
4. Failure: wrong suggestions can mislead engineers; blog stresses confidence measurement and closed feedback loop.
5. Non-LLM SOTA? Heuristic retrieval does the heavy narrowing; LLM only reorders a small candidate set.
6. Transfer: "cheap structural pruning first, LLM ranks the survivors" — same shape as documented-owner + plausible-alternatives candidate set.

**MetaRCA (China Unicom / SYSU, FSE 2026) [V]** — [arXiv 2603.02032](https://arxiv.org/abs/2603.02032)
1. Mapping: offline "Meta Causal Graph" (MCG) at the metadata/component-type level (17 component types); online: instantiate MCG onto the live service set around the fault, weight and prune links with real-time data, rank root causes (service- and metric-level). Belief per edge is a log-odds Bayesian update with asymmetric evidence weights (expert-validated incident-report evidence lambda 0.5 vs data evidence 0.05) and temporal decay k=0.005/day "to address concept drift"; online pruning threshold 0.3 — [paper](https://arxiv.org/pdf/2603.02032).
2. LLM role: OFFLINE only: Gemini 2.5 Flash bootstraps the skeleton MCG; DeepSeek-R1-70B extracts entities from 563 production incident reports. Online inference has no LLM.
3. Eval: 252 public RCAEval failures + 59 production failures. Production AC@1 (service/metric): MetaRCA 0.66/0.54; CIRCA 0.38/0.12; LLM-agent OpenRCA 0.20/0.10; CausalRCA 0.10/0.03. Time per RCA: MetaRCA 0.9 s, CIRCA 0.8 s, OpenRCA agent 384 s, CausalRCA 281 s. Ablation (production, metric AC@3): full 0.82; no report evidence 0.72; no data evidence 0.76; NO ONLINE PRUNING 0.56 (largest drop) — [paper](https://arxiv.org/pdf/2603.02032).
4. Failure/caveat: classical CIRCA beats MetaRCA on RE2-SS service AC@1 (0.86 vs 0.79); OpenRCA-agent AC@1 on RE2-OB 0.23 vs CIRCA 0.27; authors' own limits: same technology stack (China Unicom), only 59 production cases.
5. Non-LLM SOTA? Yes: the online engine is non-LLM (Bayesian belief + pruning) and beats the LLM agent by 46 pp at ~400x lower latency.
6. Transfer: closest published relative of "prior from documentation/historical reports, updated by data, decayed over time, pruned online" — but it prunes graph EDGES, it does not choose probes.

**AgentRCA (Wei & Fink, EPFL, July 2026) [V]** — [arXiv 2607.22385](https://arxiv.org/abs/2607.22385)
1. Mapping: industrial fault diagnosis. Hypothesis space = fault taxonomy in the prompt (PRONTO: 4 faults + normal; Tennessee Eastman: 10 faults + normal). Probe = 5 modular tools (autoencoder residuals, signed statistical shifts, correlation changes, temporal signatures, optional documentation retrieval) computed against a "digital twin" of normal operation matched to the current operating regime. Stopping = agent decides; hard cap 10 tool calls (never reached). Cost = ~5 tool calls, 4,615 tokens, 51 s per window (Qwen3-30B-A3B on one A100) — [paper](https://arxiv.org/pdf/2607.22385).
2. LLM role: hypothesis-driven evidence gatherer AND interpreter: it selects which tool to call next while maintaining a ranked hypothesis table with supporting/contradicting evidence. Tool selection order is not fixed and is not compared to any principled selector.
3. Eval: PRONTO (real multiphase-flow rig; test set ~105 windows per a fetch summary, not checked in raw text) Top-1/Top-2 = 87.6%/96.8% zero-shot vs supervised LightGBM 99.0%, AE-classifier 99.6%, MiniRocket+Ridge 94.5%; supervised needs >=20 labelled faulty windows per class to match zero-shot. TEP: 40.0%/61.5% vs supervised 84.1-85.7%. Models: GPT-5-mini, Qwen3-30B, Gemma4-31B, Gemma4-E4B. Reasoning-structure ablation: unstructured 83.2% < ReAct-like 85.4% < hypothesis table 87.6%; unstructured accuracy collapses at high temperature, structured does not. Removing operating-condition matching: 87.6% -> 40.6%; removing signed (directional) statistics: -> 43.8%. Documentation retrieval (PRONTO manual, fault labels redacted, unguided baseline 77.8%): +4.1 pp if given at start, +7.9 pp (to 85.7%) if given just before the final decision — [paper](https://arxiv.org/pdf/2607.22385).
4. Not shown / failures: no comparison of tool-order strategies or random ordering for query count (only a random baseline for final accuracy); a tool error (mischaracterized transient spike/sensor failure) can produce confident wrong answers; TEP gap (40% Top-1) shows ambiguity/dimensionality hurts; documentation is assumed correct (never made stale).
5. Non-LLM SOTA? Yes on accuracy: supervised classifiers beat it; its advantage is zero labelled fault data + transparent trace.
6. Transfer: the only paper here that states HVAC as a target ("heating, HVAC systems, or other sensor-rich industrial systems where labeled failures are scarce but process knowledge and documentation are abundant"); evidence that the most valuable LLM inputs are numeric, regime-conditioned, SIGNED deviation statistics — analogous to class-conditional Gaussian consistency statistics — and that late documentation retrieval (hypothesis-specific queries) helps more than early.

**AIOpsLab (Microsoft, MLSys 2025) [V]** — [arXiv 2501.06706](https://arxiv.org/abs/2501.06706)
1. Mapping: 48 problems on microservice apps; tasks detection/localization/RCA/mitigation; probes = shell/API actions; step cap 10-20.
2. LLM role: GPT-4/3.5 shell agents, ReAct, FLASH (workflow supervision + hindsight).
3. Eval (all tasks): accuracy/avg steps/tokens: GPT-4-w-Shell 49.15%/6.44/6,394; GPT-3.5-w-Shell 15.25%/14.70/2,558; ReAct 55.93%/11.50/16,941; FLASH 59.32%/8.48/6,484. Task-level: detection FLASH 100%, ReAct 76.92%; localization Acc@1 GPT-4-w-Shell 61.54%, ReAct 53.85%, FLASH 46.15%; RCA ReAct 45.45%, GPT-4-w-Shell 40.90%; mitigation ReAct 36.36%, FLASH 54.55%. Non-LLM baselines run on same telemetry: detection MKSMC 15.38%; localization PDiagnose 15.38% (Acc@1) and RMLAD 7.69% — [paper](https://arxiv.org/pdf/2501.06706). (Percentages imply only ~11-13 problems per task, so tiny N.)
4. Failure: only GPT-4-w-Shell correctly identified the no-fault ("Noop") problems; others reported false positives, mistaking normal workload activity for faults — [paper](https://arxiv.org/pdf/2501.06706).
5. Non-LLM SOTA? Here LLM agents beat the off-the-shelf classical detectors/localizers by 3-6x, but those baselines were not tuned to this data.
6. Transfer: the Noop false-positive result is the same "no mismatch exists but agent finds one" failure as FaulT-Bench (see Q2).

**ITBench (IBM/UIUC, ICML 2025) [V]** — [arXiv 2502.05352](https://arxiv.org/abs/2502.05352)
1. Mapping: SRE, CISO, FinOps scenarios on live K8s; diagnosis/mitigation pass@1 plus topology-aware fault-localization metrics (NTAM); 10 runs per scenario per model.
2. LLM role: CrewAI ReAct-style SRE agent with NL2Traces/Metrics/Logs/Kubectl tools.
3. Eval: current arXiv version: 94 scenarios (42 SRE), GPT-4o SRE diagnosis pass@1 13.81% (+/-1.67), mitigation 11.43%; CISO 25.2%; FinOps 0%. (An earlier version/leaderboard summary cited 102 scenarios and 11.4% — version difference.) Masking traces: GPT-4o diagnosis 18.10% -> 9.52% (Table 19/20). Non-determinism: same GPT-4o agent diagnosed scenario 13 in 6/10 runs, scenario 8 in 1/10, scenario 21 in 8/10 — [paper](https://arxiv.org/pdf/2502.05352). Independent leaderboard: [Artificial Analysis ITBench-AA](https://artificialanalysis.ai/evaluations/itbench-aa) [S].
4. Failure: early termination; hard scenarios ~0% mitigation; strong run-to-run variance despite tuning.
5. Non-LLM SOTA? No non-LLM baseline in ITBench.
6. Transfer: quantifies how unstable a single LLM-driven investigation is — motivates deterministic formal selector with LLM as bounded module.

**OpenRCA (Microsoft, ICLR 2025) [S abstract], OpenRCA 2.0 (CUHK-SZ, 2026) [V], "How far can RCA go on real-world telemetry" [V]**
1. Mapping: OpenRCA = 335 failures, 3 enterprise systems (Telecom, Bank, Market), 68 GB logs/metrics/traces, free-text query; RCA-agent writes Python over telemetry — [ICLR page](https://iclr.cc/virtual/2025/poster/32093), [repo](https://github.com/microsoft/OpenRCA).
2. LLM role: agent with code execution; best model Claude 3.5 solved only 11.34% — [ICLR page](https://iclr.cc/virtual/2025/poster/32093).
3. OpenRCA 2.0 (500 instances, 7.5 verified causal edges/instance, 11 frontier LLMs, ReAct): exact root-cause-set match 20.7% avg; AnySvc 76.0% vs Path Reachability 61.5% ("ungrounded diagnosis"); Node F1 62.2% vs Edge F1 43.4%; failure patterns: premature commitment, presence bias (silence read as health), salience capture (loudest downstream signal); case where Claude names the right root cause but "hallucinates a direct edge" skipping intermediate services — [arXiv 2606.27154](https://arxiv.org/abs/2606.27154).
4. "How far": on OpenRCA Market CB1, classical causal discovery (Granger, PC, FCI, LiNGAM, NTLR) scored 0% Accuracy@1; GALA 2.56%, RCLAgent 0.00%, OpenRCA agent 11.43% full score, proposed structured multi-agent 17.14% (knowledge-off) / 25.71% (domain-knowledge on; DK rules developed on test windows, so optimistic per authors); reverse-reasoning analysis says required evidence is present in most failures, so bottleneck is reasoning — [arXiv 2607.13548](https://arxiv.org/abs/2607.13548). Caveat: the "classical" methods here are generic causal-discovery methods, not tuned RCA methods (CIRCA/BARO).
5. Non-LLM SOTA? Not established on OpenRCA (generic classical = 0%); on RCAEval (metrics-only) non-LLM methods remain strong (see PRISM below).
6. Transfer: agents can name the right owner while inventing/omitting intermediate connections; a verifier of the documented CONNECTION (edge) cannot trust LLM-produced topology.

**RCAEval and classical RCA (Pham et al.) [V/S]**
- RCAEval: 735 failure cases, 3 systems (Online Boutique, Sock Shop, Train Ticket), 11 fault types, 15 reproducible baselines (metric-, trace-, multi-source) — [arXiv 2412.17015](https://arxiv.org/abs/2412.17015) [S].
- ASE 2024 "How far are we": 9 causal-discovery + 21 causal-inference RCA methods on 8 datasets; no method wins everywhere; causal discovery struggles on large graphs and edge directions; PC and FCI best discoverers; synthetic-data results do not transfer — [arXiv 2408.13729](https://arxiv.org/abs/2408.13729) [V].
- PRISM (Graph-Free RCA, RMIT, Jan 2026): non-LLM, needs no dependency graph, 68% Top-1 on 735 RCAEval failures (258% over best baseline), 8.2 ms per diagnosis — [arXiv 2601.21359](https://arxiv.org/abs/2601.21359) [V abstract/eval text]. This is the strongest "non-LLM still SOTA" datapoint found for metric-only RCA.

**GALA+ (2026) [S]** — [arXiv 2608.08968](https://arxiv.org/abs/2608.08968)
1. Mapping: dependency-graph-constrained agent investigation: top-k candidates from deterministic STRIX (trace) + BARO (metrics), then LLM investigators examine only graph neighbours (bounded expansion, O(k*max-degree)).
2. LLM role: refines rankings with localized evidence synthesis; does NOT generate initial hypotheses.
3. Eval: OnlineBoutique 90 + TrainTicket 90 injected faults (+100 AegisLab), 3 runs/case; AC@1 74.44% (OB), 73.33% (TT) vs CIRCA 66.67/53.33, BARO 14.44/66.67, RCD 64.44/10.00 (classical methods swing widely across systems); 540 reports human-graded.
4. Failure: ReAct drifts on larger graphs; mABC hallucinated service names; models paraphrase rather than cite telemetry. Robustness to wrong/stale graph: not evaluated.
5. Non-LLM SOTA? Best non-LLM baseline is 7-20 pp behind, but different classical methods win on different systems.
6. Transfer: constraining LLM steps to a documented graph neighbourhood is efficient but presumes the graph is right — the exact assumption the HVAC problem drops.

**KRCA (Kuaishou, July 2026) [S]** — [arXiv 2607.01788](https://arxiv.org/abs/2607.01788): 200k+ services; manually predefined "causal skeleton" (four meta-metric types) constrains nine expert sub-agents; 300 real incidents (Oct 2025-Mar 2026) AC@1 0.88 (service) / 0.79 (failure type), +31/+32 pts over an LLM RCA-agent; 146.6 s/case; production diagnosis time 52 -> 11.8 min. Compared only against LLM baselines; no staleness mechanism; tool-call counts not reported.

**OpsHarness (2026) [S]** — [arXiv 2608.25661](https://arxiv.org/abs/2608.25661): self-evolving knowledge/workflow harness around a general coding agent; top-1 59.0% avg vs 36.1% bare agent, 17.9% RCA-Agent, 5.6% mABC on OpenRCA+RCAEval+one industrial set; ~106k tokens/325 s per case; 37% of self-proposed rules rejected by a verification gate. Claim: "harness engineering matters more than model improvement."

**LATS-RCA (2026) [S]** — [arXiv 2605.03505](https://arxiv.org/html/2605.03505v2): MCTS-style tree search over hypotheses with reflection scoring; 91.3% on LO2 (100 cases) vs ReAct-single 39.8%, ReAct-multi 57.4%; API calls 53.1 vs 13.5 vs 25.2 (tokens 156K vs 41K vs 73K); production (37 incidents, Zoner Oy) 65.1%. Shows systematic hypothesis exploration buys accuracy at ~4x calls — the opposite of "fewer tests".

**Praxis (2025-26) [S snippet]** — [arXiv 2512.22113](https://arxiv.org/abs/2512.22113): LLM traversal over a service dependency graph (built from traces/service mesh) and a code-level program-dependence graph; reports up to 6.3x RCA accuracy and 5.3x fewer tokens vs ReAct.

**Cloud-OpsBench, SREGym, ORCA-bench, CTBench, TN-AutoRCA (benchmarks, 2025-26) [S]**
- Cloud-OpsBench (2 systems, 57 fault types, 754 cases, snapshot replay): A@1 DeepSeek-V3.2 0.73, GPT-5 0.67, GPT-4o 0.49, Claude-4-Sonnet 0.50, Qwen3-8B 0.21; steps 5.67-10.0; invalid-action rate 0.04 (GPT-5) to 0.40 (Qwen3-14B); Claude-4-Sonnet gave zero-tool diagnoses in 32% of cases ("parametric hallucination": naming a cause from the alert text without investigating); in-context examples raised GPT-4o 0.49->0.70, RAG over docs gave little; no non-LLM baseline — [arXiv 2603.00468](https://arxiv.org/abs/2603.00468).
- SREGym (90 problems, live): diagnosis success 38.1-72.6%, 19-28 read commands before first mitigation, agents "greedy pattern-match on the first anomaly" under noise; no non-LLM baseline — [arXiv 2605.07161](https://arxiv.org/abs/2605.07161).
- ORCA-bench (1,079 tasks, incl. 195 no-incident controls): best RCA accuracy 25.3% (medium) / 10.0% (hard); 26-40% of telemetry calls error or return empty; hallucination 7-40% (definition not verified) — [arXiv 2607.28545](https://arxiv.org/abs/2607.28545).
- CTBench (telecom ops, 234 tasks, LLDP-derived topology + multi-vendor inventory): best agent RCA 47.62%, path restoration 87.96%; HUMAN experts 56.4% RCA / 92.6% restoration in 40-60 min; 10.8-93.9 rounds and 0.48-3.14M tokens per task with no correlation between spend and quality — [arXiv 2608.12002](https://arxiv.org/abs/2608.12002).
- TN-AutoRCA (telecom base-station alarm RCA, 530 expert-verified cases, knowledge-graph input): direct LLM F1 <=0.6254 (0.59 on "difficult" cases, which are 94.5% of the set); LLM-generated-code evaluate-analyze-repair loop reaches F1 0.9179 (Gemini-2.5-Pro); no non-LLM baseline — [arXiv 2507.18190](https://arxiv.org/abs/2507.18190).

**Xpert (Microsoft, ICSE 2024) [S]** — [arXiv 2312.11988](https://arxiv.org/abs/2312.11988): LLM recommends KQL queries for new incidents from historical incidents (this is the nearest published "LLM proposes the next query" system); evaluated with a custom Xcore metric offline plus production deployment; I could not retrieve numeric results or any comparison to a principled query selector.

**Bayesian Orchestration of Multi-LLM Agents (2026) [S, NOT AIOps]** — [arXiv 2601.01522](https://arxiv.org/abs/2601.01522): resume-screening domain; argues LLM agents cannot compute value of information because they output discriminative posteriors, so it elicits LLM likelihoods p(evidence|state), applies Bayes with explicit priors, and lets expected-utility decide when to gather more information (34% cost reduction, N=1,000). Same architecture as the user's hybrid, but not in ops.

#### B. Head-to-head: LLM agent vs non-LLM method (accuracy)
- AIOpsLab: LLM agents beat off-the-shelf MKSMC/PDiagnose/RMLAD 3-6x on ~13 detection/localization problems — [paper](https://arxiv.org/pdf/2501.06706) [V].
- MetaRCA production: non-LLM MetaRCA 0.66 vs LLM OpenRCA-agent 0.20 (AC@1 service), 384 s vs 0.9 s — [paper](https://arxiv.org/pdf/2603.02032) [V].
- GALA+: LLM-assisted 74/73% vs best classical 67/67% AC@1 — [S](https://arxiv.org/abs/2608.08968).
- OpenRCA: generic causal discovery 0%, LLM 11-26% (all poor) — [V](https://arxiv.org/abs/2607.13548).
- RCAEval-style metric RCA: PRISM (non-LLM) 68% Top-1 in 8 ms — [V](https://arxiv.org/abs/2601.21359). No LLM-agent number on the identical 735-case protocol was found.
- Industrial process (AgentRCA): supervised classifiers beat zero-shot LLM agent (99.0% vs 87.6% PRONTO; 84.1% vs 40.0% TEP) — [V](https://arxiv.org/pdf/2607.22385).
- Many LLM papers omit non-LLM baselines entirely (Cloud-OpsBench, ITBench, NIKA, KRCA, SREGym, CTBench, TN-AutoRCA).

#### C. Is any LLM query/probe choice compared to an information-theoretic or classical selector?
- Not found in AIOps or network-operations papers (searched extensively; search budget exhausted, so absence is "not found", not "does not exist").
- Closest evidence, in order of relevance:
  - SADE (Univ. Sydney, 2026): replacing free ReAct deliberation with an explicit, phase-gated troubleshooting policy (evidence acquisition separated from hypothesis commitment; fault-family "skills") on 523 held-out NIKA incidents: root-cause F1 0.77 vs 0.40 (ReAct+GPT-5) and 0.55 (Claude Code); mean tool calls 19.9 vs 25.4 vs 26.7; TOOL CALLS PER CORRECT DIAGNOSIS 27.2 vs 49.5 vs 51.5; no-submission rate 4.2% vs 8.8% vs 15.3%. A model-controlled comparison attributes 22 of the 37 F1 points to the policy alone. The paper says the decisive step "is not broad exploration, but the selection of the check that exposes the layer at which the fault mechanism occurs" — [arXiv 2605.04530](https://arxiv.org/pdf/2605.04530) [V]. This is a scripted (human-methodology) selector beating free-form LLM selection on queries-per-success; it is not an EIG selector.
  - Flow-of-Action: SOP-constrained flow +28.5 pts accuracy but +4.3 steps vs ReAct — [V](https://arxiv.org/pdf/2502.08224).
  - LATS-RCA: search over hypotheses = ~4x API calls for +34-52 pts — [S](https://arxiv.org/html/2605.03505v2).
  - Trajectory-level study: failed runs use 7-11.4 MORE rounds than successful ones in every iterative agent; top agents spend 43-54 effective rounds and 1,500-1,700 ktok per case — [V](https://arxiv.org/pdf/2608.21310).
  - AgentRCA: hypothesis table (explicit ranked candidates) improves accuracy over unstructured tool calling (87.6 vs 83.2) at ~5 calls — [V](https://arxiv.org/pdf/2607.22385).
- Classical information-theoretic probing (pre-LLM, network diagnosis):
  - Rish, Brodie, Ma et al., "Adaptive diagnosis in distributed systems" (IEEE Trans. Neural Networks 2005): active probing selects a small number of most-informative end-to-end tests using probabilistic inference plus information theory; empirical probe reduction 60-75% (in most real-life applications) and faster localization vs non-adaptive (pre-planned) probing — [PubMed abstract via search, S](https://pubmed.ncbi.nlm.nih.gov/16252819/); earlier version with noisy-OR Bayesian networks and information-gain probe selection (probes = ping/traceroute; ~50% probe-set reduction from an information-gain heuristic; approximations "degrade gracefully" with noise) — [AAAI 2002 workshop paper, V](https://cdn.aaai.org/Workshops/2002/WS-02-15/WS02-15-013.pdf).
  - Zheng, Rish, Beygelzimer, "Efficient test selection in active diagnosis via entropy approximation" (UAI; year per arXiv listing, not verified): exact conditional entropies for next-test selection are intractable in Bayesian networks; proposes loopy-BP entropy approximation (BPEA); greedy minimum-conditional-entropy selection is within O(log N) of the optimal expected number of tests (Kosaraju et al. result), demonstrated on 485-node INET Internet-like topologies with 1-50 probe stations — [arXiv 1207.1418](https://arxiv.org/abs/1207.1418) [V].
  - Natu & Sethi (Univ. Delaware), active-probing fault localization with probe-set selection algorithm — [paper](https://www.eecis.udel.edu/~sethi/papers/06/e2emon06.pdf) [V abstract only].
  - Decision-theoretic troubleshooting (Heckerman, Breese, Rommelse, CACM 1995) is cited as foundational by Zheng et al. — [arXiv 1207.1418](https://arxiv.org/abs/1207.1418) [V reference only].

#### D. What the LLM is actually used for (pattern across systems)
- Fixed/curated selector + LLM interpretation: RCACopilot (handlers), NetAssistant (predefined workflows), Flow-of-Action (SOP flow), KRCA (predefined skeleton), GALA+ (graph neighbourhood + deterministic candidate generators), MetaRCA (offline LLM knowledge extraction only), Meta blog (heuristic retrieval, LLM ranks 20 at a time).
- LLM as free next-probe chooser: ReAct-style agents (Roy et al., AIOpsLab, ITBench, OpenRCA agent, Cloud-OpsBench, NIKA, SREGym) — the lowest-scoring family (11-25% on realistic benchmarks; higher only on synthetic injections).

### Inferences
- The literature's convergent design (human-authored or graph-constrained selector, LLM interprets/explains) is the same hybrid the user already built, but no cited system uses an EIG selector; a published LLM-vs-EIG query-count comparison on the user's benchmark would be new relative to what I could find (subject to the search-budget caveat).
- The one measured "scripted selector vs free LLM selector" number (SADE: 27.2 vs ~50 tool calls per correct diagnosis) supports the qualitative claim that structured probe selection cuts queries by ~45%, but that policy is hand-written, so it cannot be cited as evidence for EIG specifically.
- Classical active probing's 60-75% probe savings and the greedy-EIG O(log N) guarantee are the right non-LLM reference points for a "minimum number of tests" objective; AIOps benchmarks mostly do not optimize query count at all (they report steps/tokens/time because telemetry queries are cheap), so the technician-test-cost objective is closer to telecom truck-roll and classical test-selection settings than to LLM-RCA benchmarks.
- MetaRCA's ablation (online data-driven pruning gives the largest gain; documentation/report evidence outweighs statistics on real incidents; temporal decay for drift) suggests a documented prior deserves a provenance/age-dependent weight, not a fixed one.

### Gaps
- No LLM-vs-EIG (or any information-theoretic selector) head-to-head in AIOps/networking found; Xpert (LLM query recommendation) numbers not retrieved.
- Google SRE-agent work: no peer-reviewed paper found; only blog/tutorial material (not usable as evidence).
- RCAgent sample size and Xpert/StepFly/Nissist results not retrieved; StepFly ([PACMSE 2026, DOI](https://doi.org/10.1145/3808143)) and Nissist ([arXiv 2402.17531](https://arxiv.org/abs/2402.17531)) are troubleshooting-guide (TSG)-driven agents whose staleness handling I could not read.
- Huawei, Nokia, AT&T, Cisco LLM-ops papers: not found in my searches (only Ericsson vendor material, see Q3).

## Q2. How the literature treats a wrong, stale, or missing service-dependency graph / topology; any LLM work that repairs or verifies the graph itself

### Takeaway
Most LLM-RCA systems take the topology as trusted input (GALA+, mABC, KRCA, Praxis) and do not test wrong/stale graphs; the robustness work that exists is in non-LLM RCA (TORAI's missing-edge/blind-spot tests, PRISM's graph-free design, MetaRCA's runtime instantiation plus online pruning), and the one recent LLM benchmark that injects a WRONG PREMISE (FaulT-Bench, network tickets) finds tool-equipped agents resist wrong device/cause claims but over-diagnose faults when nothing is wrong. I found no LLM system evaluated on repairing or verifying a dependency graph against reality; the nearest are RIVA (LLM agents verifying deployed infrastructure against its IaC spec under unreliable tools) and OpenRCA 2.0 (which shows LLM-reconstructed propagation edges are unreliable: Edge F1 43.4%).

### Cited Findings

- Graph-based RCA assumes structural knowledge that is "often unavailable in large, evolving systems"; PRISM is designed for the case with no dependency graph, using an internal-vs-external anomaly decomposition (root cause anomalous in both internal and external properties; affected components only externally): 68% Top-1 over 735 RCAEval failures, 8 ms/diagnosis. It does NOT run a corrupted-graph experiment (an earlier fetch summary claimed it did; raw text shows it does not) — [arXiv 2601.21359](https://arxiv.org/abs/2601.21359) [V].
- Causal discovery to LEARN the graph is unreliable: struggles on large graphs and edge directions (F1 systematically below skeleton-F1); PC/FCI best; no method wins everywhere; synthetic results overstate real-system performance — [Pham et al. ASE 2024](https://arxiv.org/abs/2408.13729) [V].
- TORAI (FSE 2026, no LLM): "blind spots" = services missing from trace-built call graphs (e.g., Online Boutique 4/11, Sock Shop 11/11, Train Ticket 37/64 by default). Sensitivity sweep 0-100% blind spots: Online Boutique AC@1 ranges 64.4-88.9% (80% AC@1, 95% AC@3 with NO traces); Train Ticket Avg@5 falls from 89% (0% blind) to a minimum 71.6% (70% blind) and recovers at 100% (74% AC@1, 84% AC@3) because it falls back to metrics+logs; AC@3 stays >74% (TT) and >82% (OB). Design choice: does not reconstruct the call graph. (Fetch-tool summary gave a wrong 56% figure; raw text corrected.) — [arXiv 2604.13522](https://arxiv.org/abs/2604.13522) [V].
- MetaRCA (see Q1 card): does not trust a static system graph; builds reusable metadata-level causal patterns, instantiates them onto the current service set, then weights/prunes edges with real-time data; removing online pruning is the largest ablation drop (metric AC@3 0.82 -> 0.56); temporal decay (k=0.005/day) is explicitly for "concept drift in evolving systems" — [arXiv 2603.02032](https://arxiv.org/abs/2603.02032) [V]. LLM used only offline (Gemini 2.5 Flash, DeepSeek-R1-70B) to bootstrap/extract knowledge; the paper itself says LLM-based RCA is "plagued by hallucinations, high inference latency, and prohibitive operational costs".
- GALA+ explicitly does not evaluate incorrect/stale dependency graphs (external-validity threat) — [arXiv 2608.08968](https://arxiv.org/abs/2608.08968) [S]. KRCA: skeleton is manually predefined; no staleness mechanism discussed — [arXiv 2607.01788](https://arxiv.org/abs/2607.01788) [S]. mABC's Dependency Explorer queries a given global topology — [paper](https://arxiv.org/pdf/2404.12135) [V].
- Where dependency edges are exposed to LLM scoring: OpenRCA 2.0 shows agents identify a right service 76.0% but ground it in a verified propagation path 61.5%; Node F1 62.2% vs Edge F1 43.4%; concrete example of a hallucinated direct edge skipping two intermediate services — [arXiv 2606.27154](https://arxiv.org/abs/2606.27154) [V]. Trajectory-level study: agents leave 54-68% of propagation edges untested ("untested propagation edges") and fabricate out-of-schema causes in 20-82% (model-dependent) of failed cases — [arXiv 2608.21310](https://arxiv.org/abs/2608.21310) [V].
- FaulT-Bench (Univ. Sydney, Aug 2026): 200 scenarios over 8 network topologies with four ticket classes: Correct-Fault (80), False-Premise (72: network healthy, ticket reports a fault), Wrong-Device (24), Wrong-Cause (24); plus 360 persona rewrites of the false-premise tickets. Three agents (SADE, NIKA ReAct, Claude Code) are near-saturated on accurate tickets and robust to misdirection (Wrong-Device shifts accuracy by +2.5 pp, Wrong-Cause by -2.1 pp vs Correct-Fault), but on healthy networks they invent a fault: SADE 24% (51/210 answered runs), ReAct 16% (33/209), Claude Code 11% (21/198). The traces show they "correctly disprove the reported symptom" but keep probing until a benign standing condition can be promoted to a root cause. A confidently wrong report is handled about as well as an accurate one; a vague report degrades performance most (Naive-unsure raises over-diagnosis 16% -> 35%; deleting identifiers raises it to 47%); ticket phrasing alone moves accuracy up to 14.5 pp — [arXiv 2608.27021](https://arxiv.org/pdf/2608.27021) [V].
- ORCA-bench includes 195 no-incident control tasks and reports hallucination 7-40% across models — [arXiv 2607.28545](https://arxiv.org/abs/2607.28545) [S]; AIOpsLab's Noop problems: only GPT-4-w-Shell said "no fault"; others flagged normal workload activity — [arXiv 2501.06706](https://arxiv.org/pdf/2501.06706) [V].
- RIVA (EPFL/armasuisse, Mar 2026): LLM agents verify deployed infrastructure against its Infrastructure-as-Code spec ("configuration drift": deployed state diverges from documented spec through IaC bugs, manual changes, updates). Core problem: an agent cannot tell whether an anomalous tool output reflects real drift or a broken tool. With one erroneous tool, baseline ReAct success fell 22.2% -> 11.1% (localization) and 50.0% -> 40.0% (detection). RIVA (verifier agent + tool-generation agent, K independent probe paths per property, tool-call history) recovers accuracy from 27.3% (ReAct, erroneous tools) to 50.0%; 28% -> 43.8% with correct tools; K=2 works, K=3 gave 0% because AIOpsLab lacks three distinct diagnostic paths per property. Tiny N (reported percentages such as 22.2%, 11.1%, 27.3% imply roughly 9-11 tasks per cell) — [arXiv 2603.02345](https://arxiv.org/abs/2603.02345) [V].
- Documented procedures also go stale: RCACopilot motivation lists outdated TSG content as a primary pain point — [paper](https://arxiv.org/pdf/2305.15778) [V]. Architecture-drift material (documented dependencies diverging from runtime; runtime tracing has "high cost and low coverage") is practitioner/blog-level in my results — [search snippet DEV.to](https://dev.to/eko/architecture-drift-detection-keep-your-code-aligned-with-design-kae) [S, weak].

### Inferences
- The LLM literature almost never manipulates topology correctness as an experimental factor; the HVAC "documented owner may be wrong" setting is therefore genuinely under-studied there. The nearest controlled analog is FaulT-Bench's false-premise class, which frames the failure as over-diagnosis (no abstention) rather than anchoring on the documented claim.
- FaulT-Bench evidence cuts against the assumption that tool-equipped agents blindly anchor on a wrong stated premise when the premise is specific and testable (shift within about 2.5 pp); it supports instead "agents cannot conclude nothing is wrong". For the HVAC verifier this argues for (a) an explicit "documentation correct" hypothesis in the posterior, (b) a stopping/futility rule that the LLM cannot override, and (c) reporting false-mismatch rate on correct documentation as a first-class metric.
- Non-LLM designs handle uncertain topology by (i) not needing it (PRISM, TORAI), or (ii) treating it as a prior updated and pruned by data with age-weighted evidence (MetaRCA). Both are compatible with a categorical posterior over documented + alternative owners.
- RIVA's point (a surprising reading may be a broken instrument, not a real change) maps to sensor faults/miscalibration in HVAC; only multi-path cross-validation, not the LLM, resolved it.

### Gaps
- No LLM paper found that repairs or verifies a service dependency graph against reality with a quantitative evaluation; RIVA is IaC-vs-deployment, not service graph.
- No systematic "topology staleness rate" study for microservice service maps found; drift numbers are practitioner claims.
- Persistence/aging models for documented edges (beyond MetaRCA's fixed decay constant) not found.

## Q3. Network / telecom side: inventory-vs-reality reconciliation, topology discovery by active probing, LLM agents for network troubleshooting/config verification; where LLMs help and where formal methods still win

### Takeaway
Operator practice (ByteDance NetAssistant, Microsoft/Meta/Alibaba SIGCOMM papers) uses LLMs for intent parsing, config/text understanding and hypothesis/explanation while diagnostic logic stays in predefined workflows or formal verifiers; benchmarks show agents at 23-55% RCA accuracy with humans at only 56% on the hardest telecom tasks. Classical active probing/tomography (Rish/Brodie/Ma, Doubletree) chooses probes by information gain or redundancy avoidance and cut probes 50-75%; and formal verifiers (Batfish/Campion) turned unreliable GPT-4 config synthesis into workable output. For inventory reconciliation I found only vendor/practitioner material (no peer-reviewed LLM evaluation).

### Cited Findings

#### A. Inventory / CMDB vs reality (all vendor or practitioner sources; treat as unverified)
- Vendor blog states "most organizations find 30 to 50 percent drift" when auditing 200-500 CMDB items against discovery, and "industry research puts the average CMDB accuracy at roughly 60 percent" — neither is attributed to a named study in the page text — [Virima](https://virima.com/blog/cmdb-tco-analysis) [S, unattributed vendor claim]. A search snippet from a Virima page also gave "15 to 25 percent per quarter" drift in active development environments and "fewer than half of IT leaders trust their CMDB data enough to automate" (attributed to Flexera 2024 State of ITAM); I could not confirm either on the page I fetched — [Virima search result](https://virima.com/blog/cmdb-tco-analysis) [S, unverified].
- Product-level mechanisms: ServiceNow CMDB drift-detection engine and BMC Helix drift management compare CMDB state to discovered state — [ServiceNow community](https://www.servicenow.com/community/cmdb-forum/improving-cmdb-accuracy-with-drift-detection-engine/m-p/3410374), [BMC docs](https://docs.helixops.ai/bin/Service-Management/IT-Service-Management/BMC-Helix-CMDB/ac262/Using/Tracking-configuration-drift/Drift-management-overview/) [S, search snippets].
- Telecom: reconciliation is the comparison of records vs actual network data (disconnected services still billed, services in use but not in inventory, stale locations) — [Datafield](https://datafieldusa.com/telecommunications-network-reconciliation/), [ServiceNow telecom discovery primer](https://www.servicenow.com/community/telecom-blog/telecom-network-discovery-primer/ba-p/3015373) [S, vendor]. LLM claim: "LLMs can expose gaps in stored data" and raise reconciliation alerts — [CORTEX](https://www.wearecortex.com/large-language-models-can-boost-telecoms-inventory-management-and-data-exchange/) [S, vendor opinion, no evaluation].
- Ericsson positions agentic RAN troubleshooting with a knowledge graph (ontology-driven orchestration; reasoning across topology, time, incident history) — white paper/blog, no evaluation numbers — [Ericsson white paper](https://www.ericsson.com/en/reports-and-papers/white-papers/adapting-agentic-ai), [Ericsson blog 2026](https://www.ericsson.com/en/blog/2026/6/from-data-to-decisions-make-agentic-ai-driven-telecom-operations-a-reality) [S, vendor].

#### B. Classical topology/fault probing (non-LLM)
- Rish/Brodie/Ma et al. (IBM): probes = ping/traceroute-style test transactions; adaptive selection by information gain over a Bayesian network (noisy-OR); 60-75% fewer probes than pre-planned probing on real applications — see Q1.C sources.
- Doubletree (Donnet, Raoult, Friedman, Crovella): coordinated traceroute that starts mid-path and stops when it reaches already-known hops, reducing intra- and inter-monitor redundancy while discovering nearly all interfaces/links that classical tracerouting finds — [arXiv cs/0411013](https://arxiv.org/abs/cs/0411013) [S, search snippet]. Yarrp (randomized high-speed IPv4 topology probing) — [arXiv 1605.03999](https://arxiv.org/abs/1605.03999) [S].
- "Bayesian Probing on Graphs" (2026): adaptive vs non-adaptive edge probing with Bayesian updates; approximation bounds; application domain fraud/drug discovery, not networks — [arXiv 2606.09729](https://arxiv.org/abs/2606.09729) [S, tangential].
- Not retrieved: network tomography surveys (Vardi 1996; Castro et al. 2004), "Topology Discovery by Active Probing" — listed under Gaps.

#### C. LLM agents in network troubleshooting and configuration (2023-2026)
- NetAssistant (ByteDance, NSDI 2024): deployed 3+ years in data centers, hundreds of uses per day. LLM used ONLY for intent understanding (few-shot multiple-choice intent classification); diagnosis logic is predefined workflow functions learned from network engineers. Authors report LLMs are good at static information (e.g., how a QoS system works, change SOP) but "challenging" for diagnostic logic and real-time monitoring data. Monthly false-positive rate 8.45-12.33%, false-negative 0-1.25% (a false negative found in postmortem was a switch-loopback port not covered by monitoring) — [NSDI paper](https://www.usenix.org/conference/nsdi24/presentation/wang-haopei) [V].
- NIKA (Wang et al., 2025): 640 incident scenarios, 54 issue types, 5 network scenario families, live Kathara labs with 30+ MCP tools; on a 150-incident subset GPT-5 detection 89%, localization 68.7%, RCA 55.3% (GPT-5-mini 74/36/22, GPT-OSS-20B 19/5.5/5.5); GPT-5 averaged 28.4 tool calls/incident (0.7% tool errors); agents settle on "shallow connectivity-centric explanations"; localization degrades on larger topologies; no non-LLM baseline — [arXiv 2512.16381](https://arxiv.org/abs/2512.16381) [S].
- SADE (2026): see Q1.C (scripted phase-gated policy; 27.2 vs 49.5 calls per correct diagnosis) — [arXiv 2605.04530](https://arxiv.org/pdf/2605.04530) [V].
- FaulT-Bench (2026): see Q2; cost side: real-fault runs cost 13-18 tool calls per answered run; vague tickets cost ~30 calls and ~4x tokens (549k vs 136k per answered run); 9% of runs time out but consume 23% of spend (US$1,525 total for 3,960 runs; ~US$165 and ~59 h per core pass of 200 scenarios) — [arXiv 2608.27021](https://arxiv.org/pdf/2608.27021) [V].
- CTBench (2026): telecom troubleshooting with LLDP-derived topology and multi-vendor inventory; best agent 47.62% RCA vs human experts 56.4%; even correct answers often lack evidence-grounded diagnoses; 15.08% of RCA tasks have partial observability (direct diagnostic command unavailable) — [arXiv 2608.12002](https://arxiv.org/abs/2608.12002) [S].
- NetConfEval (CoNEXT 2024): four config tasks (spec translation, API/function-call generation, routing algorithm generation, low-level config from documentation); evaluation is largely static — [ACM](https://dl.acm.org/doi/10.1145/3656296) [S]. NetConfArena (2026): 480 executable closed-loop instances, 3,840 trajectories; DeepSeek v4-pro 85.2% pass, Qwen3-8B 4.6-9.4%; failures: knowledge deficiency, unproductive hesitation, premature abandonment, specification deviation; stronger agents spend 52-59% of actions on validation; does not compare against Batfish/formal verifiers — [arXiv 2608.23179](https://arxiv.org/abs/2608.23179) [S]. NetArena (2026): agents 13-38% average on large realistic network-automation queries (as low as 3%) — [arXiv 2506.03231](https://arxiv.org/abs/2506.03231) [S].
- Formal verifier + LLM: Mondal et al. (HotNets 2023): GPT-4 alone "works very badly" (errors in topology, syntax, semantics); "verified prompt programming" using Batfish (syntax) and Campion (semantics/policy) feedback automates correction; automated prompts give 10x leverage for Cisco-to-Juniper translation and 6x for a no-transit policy, but humans still needed — [arXiv 2307.04945](https://arxiv.org/abs/2307.04945) [S]. Related work on NetConfEval-style disambiguation: [arXiv 2507.12443](https://arxiv.org/pdf/2507.12443) [S, title only].
- SIGCOMM 2025-2026 industry systems identified but NOT read (ACM DL blocked): Alibaba "Towards LLM-Based Failure Localization in Production-Scale Networks" (SIGCOMM 2025), Meta "Confucius" multi-agent intent-driven network management (SIGCOMM 2025), Alibaba AIDA multi-vendor device-failure RCA (SIGCOMM 2026), Alibaba "Networked Agent Memory and Causality Representation" (SIGCOMM 2026) — titles/venues from the FaulT-Bench reference list [V for existence](https://arxiv.org/pdf/2608.27021).

#### D. Where LLMs help vs where formal methods still win (as stated by authors)
- LLM helps: intent/ticket understanding (NetAssistant), static knowledge/config text and doc parsing (NetAssistant; NetConfEval task 4), hypothesis/report generation and explanation (RCACopilot, Meta blog), code generation over telemetry (OpenRCA agent, TN-AutoRCA code loop) — cited above.
- Formal/classical wins: correctness of config semantics (Batfish/Campion loop), predefined diagnostic workflows for real-time monitoring data (NetAssistant), information-gain probe scheduling (Rish et al.), millisecond metric-only localization (PRISM, MetaRCA online engine, CIRCA), and stopping/abstention ("nothing is wrong": FaulT-Bench).

### Inferences
- In telecom/network practice the "documentation" (ticket, inventory, TSG, IaC spec) is treated as a claim to be verified by live probes, and the winning production pattern keeps probe choice in predefined workflows or formal verifiers; that is consistent with a formal EIG layer deciding and an LLM parsing/explaining.
- Operators' probe economics differ: network/AIOps probes are cheap and fast, so the literature optimizes accuracy and token cost; physical HVAC tests (duct trace, actuate-and-observe) resemble truck-roll/field-verification costs, where the classical active-probing objective (fewest probes for a target error) is the right lens.
- The 2005 active-probing result (60-75% probe savings) is the best available prior for how much adaptive information-gain selection can save relative to fixed/pre-planned procedures; the LLM literature offers no comparable number.

### Gaps
- No peer-reviewed evaluation of LLM agents for inventory-vs-reality reconciliation found; CMDB drift percentages are vendor claims of unknown provenance.
- Not read: Alibaba BiAn/AIDA/Ren et al. (SIGCOMM), Meta Confucius, TN-AutoRCA follow-ups, any Nokia/Huawei/AT&T/Cisco LLM-ops papers (none surfaced), classical tomography literature (Vardi, Castro et al.), "Topology Discovery by Active Probing". Reason: ACM DL HTTP 403 and web-search budget exhausted.
- Doubletree/Yarrp claims are search-snippet level, not full-text verified.

## Q4. Reported failure modes when LLM agents choose the next query, and measured "number of queries to root cause"

### Takeaway
Reported failures cluster into: unproductive search (failed runs use 7-11 more rounds than successful ones), premature commitment to the loudest or first anomaly, inability to abstain (over-diagnosis on healthy systems), ungrounded/hallucinated propagation edges and non-existent entities, invalid or empty tool calls, high run-to-run variance, and large token/time cost; anchoring on a wrong documented premise is reported in some settings but was NOT the dominant failure in the one controlled test (FaulT-Bench). Query counts per success range from ~5 to ~50 depending on system, and structured/scripted selectors reduced calls per correct diagnosis by ~45% (SADE) while free-form or tree-search agents used more calls.

#### B. Failure modes with evidence
- Wasted/unproductive queries: failed runs run more rounds than correct ones in every iterative arm, "unproductive search inflates cost without improving outcomes"; successful runs stay on the fault-impact surface and act on retrieved evidence, failed ones "depart from the relevant route, fail to use decisive observations, or stagnate in shallow, repetitive queries" — [arXiv 2608.21310](https://arxiv.org/pdf/2608.21310) [V]. Spend does not track quality (CTBench) — [S](https://arxiv.org/abs/2608.12002). Timeouts: 9% of FaulT-Bench runs consume 23% of spend — [V](https://arxiv.org/pdf/2608.27021). Cloud-OpsBench: small models loop on invalid payloads (invalid-action rate 0.40) — [S](https://arxiv.org/abs/2603.00468); ORCA-bench: 26-40% of telemetry calls error/empty — [S](https://arxiv.org/abs/2607.28545).
- Anchoring / early commitment: "anchor lock" (early hypothesis retained after conflicting evidence) in 28-34.6% of failed cases (Sonnet/Qwen pools of 50/104) — [V](https://arxiv.org/pdf/2608.21310); premature commitment (stop after one plausible root cause) and salience capture (converge on the loudest downstream signal) — [V](https://arxiv.org/abs/2606.27154); SREGym "greedy pattern-matching on first anomaly" under noise — [S](https://arxiv.org/abs/2605.07161); ORCA-bench "lock onto louder symptoms" — [S](https://arxiv.org/abs/2607.28545); Waterloo taxonomy lists anchoring bias, failure to update beliefs, evidential insufficiency among 16 reasoning failures across six open models on 48,000 fault scenarios (FORGE 2026) — [S](https://uwaterloo.ca/waterloo-intelligent-systems-engineering-lab/projects/llm-reasoning-failures-cloud-root-cause-analysis).
- Anchoring on a WRONG DOCUMENTED premise specifically: not the dominant failure in FaulT-Bench (misdirection shifts accuracy by +2.5/-2.1 pp); vague/unfalsifiable premises and healthy systems are the hard cases — [V](https://arxiv.org/pdf/2608.27021). A summary-tool description claiming agents "blindly anchor on wrong tickets" contradicted the paper and is discarded.
- Inability to conclude "nothing wrong": over-diagnosis in 11-24% of healthy-network runs (up to 47-51% under vague/uncertain tickets for one agent) — [V](https://arxiv.org/pdf/2608.27021); AIOpsLab Noop false positives — [V](https://arxiv.org/pdf/2501.06706).
- Protocol omission and misreading: missing baseline comparisons 26-52%, untested propagation edges 54-68%, absent resource probes 34-64%; silence read as health 30-44%; salience bias 32-42%; telemetry read with wrong service semantics 62-86% (percentages are within-model failure-pool prevalence, n=50 Sonnet / n=104 Qwen) — [V](https://arxiv.org/pdf/2608.21310).
- Parametric hallucination / skipping investigation: Claude-4-Sonnet gave zero-tool diagnoses in 32% of Cloud-OpsBench cases — [S](https://arxiv.org/abs/2603.00468).
- Hallucinated dependencies/entities: hallucinated direct edge and Edge F1 43.4% — [V](https://arxiv.org/abs/2606.27154); fabricated out-of-schema causes 20-82% of failure pool — [V](https://arxiv.org/pdf/2608.21310); mABC non-existent service names — [S](https://arxiv.org/abs/2608.08968); schema hallucination of tool parameters — [S](https://arxiv.org/abs/2603.00468).
- Unconstrained exploration: ReAct drifts on larger graphs; constraining to a graph neighbourhood or skeleton helps (KRCA: constrained LLM >60% vs unconstrained ~30% as anomalous metrics increase — [S](https://arxiv.org/abs/2607.01788)); localization degrades with topology size (NIKA) — [S](https://arxiv.org/abs/2512.16381); SADE holds up on >100-node topologies — [V](https://arxiv.org/pdf/2605.04530).
- Inconsistent repeat runs: ITBench GPT-4o same-scenario diagnosis success 1/10, 6/10, 8/10 across scenarios despite hyperparameter tuning — [V](https://arxiv.org/pdf/2502.05352); GALA and RCACopilot average 3 runs; AgentRCA unstructured reasoning collapses at high temperature while structured (hypothesis-table) does not — [V](https://arxiv.org/pdf/2607.22385); NetArena reports dynamic benchmark generation reduced confidence-interval overlap from 85% to 0% (variance problem in static sets) — [S](https://arxiv.org/abs/2506.03231); one small-model study claims multi-agent orchestration gives zero quality variance (TinyLlama-1B, single authentication scenario, 348 trials, automated scoring only) — [S, low quality](https://arxiv.org/html/2511.15755v2).
- Removing a decisive evidence source collapses performance: masking traces cuts GPT-4o diagnosis 18.10% -> 9.52% (ITBench) — [V](https://arxiv.org/pdf/2502.05352); AgentRCA removing regime matching 87.6% -> 40.6% — [V](https://arxiv.org/pdf/2607.22385); removing source-code access -9 to -16 pp (ORCA-bench) — [S](https://arxiv.org/abs/2607.28545).
- Correct answer, wrong reasoning: OpenRCA 2.0 (14.5 pp gap), CTBench (plausible/correct final answers without evidence-grounded diagnoses) — [V](https://arxiv.org/abs/2606.27154), [S](https://arxiv.org/abs/2608.12002).
- Erroneous instrument outputs: single broken tool halves accuracy (22.2% -> 11.1%; 50.0% -> 40.0%) — [V](https://arxiv.org/abs/2603.02345).

### Inferences
- For "minimize technician tests", the AIOps evidence supports three design constraints: (i) LLM agents' spent effort is a poor proxy for progress (failed runs cost more), so a hard budget/futility rule outside the LLM is justified; (ii) a stop rule outside the LLM addresses both premature commitment and non-termination (SADE's stop-and-submit rule reduced no-submission failures 80 -> 22 cases vs Claude Code on 523 incidents, [V](https://arxiv.org/pdf/2605.04530)); (iii) evidence-source reliability needs its own hypothesis (RIVA).
- Because ITBench-style variance is measured per scenario (1/10 to 8/10 success), any comparison of an LLM selector to EIG on the user's benchmark should use many repeats (>=10) per case and report per-case variance, not just means.
- Query counts in this literature are not comparable to technician tests: they include cheap telemetry reads; only SADE, FaulT-Bench, AIOpsLab and Rish et al. treat "number of probes" as an outcome with explicit accounting.

### Gaps
- No paper reports the information gain of individual LLM-chosen queries (e.g., realized entropy reduction per query) or compares an LLM's chosen next query to an oracle/greedy-EIG choice on the same state.
- No cost model with heterogeneous per-query cost (physical test vs data read) in the LLM-RCA benchmarks; only token/time cost.
- Numbers tagged [S] (Cloud-OpsBench, SREGym, ORCA-bench, CTBench, NIKA, LATS-RCA, KRCA, OpsHarness, Roy et al.) have not been checked against raw text and some fetch summaries proved unreliable.
